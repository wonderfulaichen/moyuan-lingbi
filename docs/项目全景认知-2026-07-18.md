## 1. 项目定位与一句话描述

| 维度 | 内容 |
|------|------|
| **产品名称** | 墨渊灵笔（moyuan-lingbi） |
| **定位** | 纯本地 AI 辅助小说创作工坊 |
| **Slogan** | 帮助作者从灵感萌发到完成整部小说 |
| **核心差异** | GUI 三栏可视化创作 + DAG 调度 Agent 流水线双引擎；数据全部本地存储，支持云端 LLM 与本地 `.gguf` 模型离线运行 |
| **当前版本** | v0.3.7（`package.json` 第 4 行） |

**核心价值**：
1. **GUI 是护城河**：把 AI 创作过程“看得见、可干预、能回退”。
2. **Agent 是攻城锤**：基于 DAG 的 Agent 流水线，实现从灵感、大纲、角色、剧情到成稿的多 Agent 协同，而非单轮问答。

---

## 2. 目标用户与使用场景

- **目标用户**：中文小说创作者、网文作者、 amateur 写手、需要长文本一致性的内容创作者。
- **典型场景**：
  - 输入一句话灵感，AI 发散标签 → 生成多个小说方案 → 确认方案。
  - 在可视化文件树中管理世界观、角色、时间线、大纲、细纲、章节。
  - 与右侧 AI 助手对话，自动创建/更新文件、续写章节、审校一致性。
  - 使用本地大模型离线创作，避免隐私泄露。

### 4.4 Agent 流水线

```
用户指令
    │
    ▼
┌──────────────────┐
│   创作助手（主 Agent） │  ← 统一入口，自动路由
│  ai-assistant/   │
└────────┬─────────┘
         │
    ┌────┴────┬──────────┬──────────┐
    ▼         ▼          ▼          ▼
Writer    Auditor   Revisor   Planner/Researcher/Memory
(写手)    (审计员)  (润色师)  (规划/研究/记忆)
    │         │          │          │
    └─────────┴────┬─────┴──────────┘
                   ▼
          ┌─────────────────┐
          │   Skill 能力层   │
          │ tokenSaver      │
          │ contextCompress │
          │ consistencyCheck│
          └─────────────────┘
                   │
                   ▼
          ┌─────────────────┐
          │  工具执行层      │
          │ create_file     │
          │ update_file     │
          │ read_file       │
          │ search          │
          └─────────────────┘
```

**AgentRuntime 关键机制**：
- DAG 依赖解析：`internal/DependencyResolver.ts` 使用 Kahn 算法拓扑排序、检测循环依赖。
- 单步执行：`internal/StepRunner.ts` 执行 LLM 调用，含指数退避重试、取消信号。
- 取消机制：`internal/CancellationToken.ts` 提供 `CancellationToken` / `CancelledError`。
- 注册表：`AgentRegistry.ts` 注册 5 个内置 Agent 与 5 个子 Agent，并维护任务类型映射。

### 4.5 数据流

1. **VFile 系统**：每个项目拥有独立的 `VFileSystem`（`files: Record<string, VFile>` + `rootIds`），通过 `DataService` 统一读写。
2. **观察者模式**：`DataService.subscribe(listener)` 在数据变更时触发 UI 刷新与持久化。
3. **持久化**：默认 `localStorage`（`moyuan-v2-data`）；Electron 下通过 `StorageProvider` 写入文件系统；容量接近 5MB 时告警。
4. **Memory Bank 同步**：AI 处理前，`processWithAI` 调用 `memoryBankService.syncFromFileSystem()` 把文件系统内容同步到长期记忆体。
5. **AI 上下文注入**：`aiService.generateWithContext` 自动拼接“项目正典内容”，确保 AI 不违背已收藏设定。

## 6. 安全与密钥管理

| 项 | 说明 |
|------|------|
| **API Key 存储** | 无 `.env`，在应用内 Settings 配置，经 `DataService` 持久化到本地 |
| **加密策略** | 优先 OS 原生 `safeStorage`（Windows Credential Manager / macOS Keychain）；不可用时降级为 XOR + 每安装随机密钥 |
| **密文前缀** | `safe:` 表示 safeStorage；`enc:` 表示 XOR 降级；无前缀为旧明文 |
| **内存缓存** | 启动时解密所有 API Key 缓存到内存 Map，`getActiveModel/getModels` 可同步读取 |
| **迁移路径** | `migrateApiKeys()`：旧固定密钥 XOR → 新随机密钥 XOR；`upgradeToSafeStorage()`：XOR → safeStorage |
| **本地模型** | 支持离线 `.gguf` 推理，无需 API Key |
| **Android 签名** | 仓库存在 keystore 文件，alias / 密码需线下单独移交，严禁入仓库 |

**当前状态**（基于交接文档）：`main.js`/`preload.js` 已暴露 safeStorage IPC，但 `DataService.ts` 中 safeStorage 集成已完成（`secureEncrypt/secureDecrypt` 优先 safeStorage）。

## 8. 当前风险与技术债

### 8.1 遗留 P0（高风险）

| 编号 | 问题 | 文件 | 当前状态 |
|------|------|------|----------|
| **P0-1** | `DataService.getFS/getData/getActiveProject` 返回可变引用，外部可直接修改内部状态，破坏观察者模式 | `DataService.ts` | 已加 DEV 模式只读 Proxy 探测；类内方法已改为直接操作 `this.data` 避免经 getter 修改；全面根治需后续返回只读视图 |
| **P0-4** | `StepMemoryService` 声称不可变但实际直接修改缓存 step 属性 | `StepMemoryService.ts` | **已修复**：`updateStepStatus`、`completeStep`、`addDependency`、`cascadeUnblockDependents`、`addStepToChain` 均已采用写时拷贝生成新 Step 数组；`StepChain` 对象仍有 TODO 待完善 |

### 8.2 架构级风险

1. **双 Agent 系统边界不清**：`ai-assistant/index.ts`（旧单体创作助手）与 `agent-runtime/`（新 DAG 引擎）各自维护 Agent 生命周期，协作关系需要进一步收敛。
2. **localStorage 容量上限**：全量 JSON 序列化保存项目数据，单项目过大时会触发 5MB 配额告警。
3. **数据变更 emit 全量持久化**：每次 `emit()` 都会 `JSON.stringify` 并写入存储；虽然 `scheduleSave` 有 150ms 防抖，但流式输出仍可能高频触发。
4. **移动端未稳定**：`src/renderer/app/mobile/` 标注调试中，布局与交互尚未成熟。
5. **游离功能待整合**：番茄钟、白噪音、成就系统存在但未必已接入主创作流。

### 8.3 已修复的重要问题

- P0-2：`StepRunner` 超时定时器与 abort 监听器泄漏 → 已用 `finally` 统一清理。
- P0-3：`emit()` 持久化去抖 → 已引入 `scheduleSave` 防抖。
- P0-5 / P0-6 / P0-7 / P0-8 / P0-9：布局嵌套、消息角色、FileViewer、Review/Memory 入口冲突、Hooks 违规 → 已修。
- 测试失败：`MemorySearchService.test.ts` 排序逻辑错误、`ResearcherAgent.test.ts` mock 问题、`StepRunner.parseLLMResponse` 成功路径缺 `success:true` → 已修。

4. **移动端补齐**：先完成核心创作流程（灵感 → 设定 → 写作）的移动端适配，再扩展高级功能。
5. **测试回归**：每次改动后运行 `npm run test:run`，保持 211 passed / 0 failed。

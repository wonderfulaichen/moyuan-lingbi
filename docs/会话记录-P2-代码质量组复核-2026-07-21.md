## 三、重写方案

### 3.1 架构：useState + useRef 混合模式

**核心思路**：
- `history`/`currentIndex` 用 `useState` 管理 → 修改时触发重渲染 → `canUndo`/`canRedo`/`clearHistory` 自动更新
- `valueRef`/`historyRef`/`indexRef` 用 `useRef` 保存最新值 → 避免连续调用时闭包陷阱

**为什么不用单一 useRef**：`canUndo = currentIndex > 0` 是渲染期计算的派生值，若 history/currentIndex 是 ref，则 canUndo 永远是初始值 0/false，撤销按钮永远禁用。

**为什么不用单一 useState**：setValue 在同一 tick 内可能被调用多次（如 MAX_HISTORY 测试连续 105 次），每次都从闭包读取 state 会读到旧值，导致 history 栈错乱。

### 3.2 副作用隔离

**原实现**（错误）：
```typescript
setHistory(prev => {
  onChange?.(resolved);  // 副作用在 updater 内
  return newHistory;
});
```

**新实现**（正确）：
```typescript
// 副作用通过 useEffect 触发，移出 setState updater
useEffect(() => {
  onChangeRef.current?.(value);
}, [value]);
```

**理由**：React 18 StrictMode 下 updater 会被调用两次（用于检测纯函数性），副作用必须在 updater 外执行。同时用 `onChangeRef` 保存最新的 onChange，避免 useEffect 依赖 onChange 导致频繁重建。

### 3.3 章节切换清空历史栈

**WritingEditor 集成修复**：
```typescript
// 切换章节时同步内容并清空历史栈，避免撤销跨章节串内容
useEffect(() => {
  setEditorContent(currentContent, true);
  clearHistory();
}, [editingChapterId]); // eslint-disable-line react-hooks/exhaustive-deps
```

**原 bug**：切换章节后撤销会回到上一章节的内容，因为历史栈没有清空。

## 四、aiStatusStore 竞态修复

### 4.1 问题分析

`setComplete` 中 setTimeout 3 秒后清空 `statusMessage`/`progress`：

```typescript
// 原实现
setComplete: () => {
  set(s => ({ isGenerating: false, /* ... */ }));
  setTimeout(() => {
    set(s => ({ statusMessage: '', progress: 0 }));
  }, 3000);
}
```

**竞态场景**：
1. 任务 A 完成 → setComplete → 启动 3 秒定时器 T1
2. 1 秒后用户启动任务 B → setGenerating（isGenerating=true）
3. 2 秒后 T1 触发 → 检查 isGenerating（此时为 true，正确地 return s）
4. **但若 T1 检查时机在 setGenerating 之前**：清空 statusMessage/progress，新任务状态被误清

更严重的是连续 setComplete：
1. 任务 A 完成 → setComplete → 启动 T1
2. 任务 B 完成 → setComplete → 启动 T2（T1 未清理）
3. T1 触发 → 清空
4. T2 触发 → 再次清空（无意义但无害）
5. **若 T1 触发时刚好新任务启动**：误清新任务状态

### 4.2 修复方案：模块级定时器 + 入口清理

```typescript
// 模块级定时器
let completeResetTimer: ReturnType<typeof setTimeout> | null = null;

function clearCompleteResetTimer() {
  if (completeResetTimer) {
    clearTimeout(completeResetTimer);
    completeResetTimer = null;
  }
}

// setComplete 中
clearCompleteResetTimer();  // 先清旧
completeResetTimer = setTimeout(() => {
  completeResetTimer = null;
  set(s => {
    if (s.isGenerating) return s;  // 若新任务已启动，不清
    return { statusMessage: '', progress: 0 };
  });
}, 3000);

// setGenerating 入口
setGenerating: (...) => {
  clearCompleteResetTimer();  // 新任务启动，清掉挂起的清空定时器
  // ...
}

// resetStatus 入口
resetStatus: () => {
  clearCompleteResetTimer();  // 手动重置，清掉挂起的清空定时器
  // ...
}
```

### 4.3 设计模式：Zustand 模块级定时器

**为什么用模块级变量**：Zustand store 是单例，没有组件生命周期。定时器若放在 store state 中会导致：
1. 状态污染（timer id 不应作为业务状态）
2. 持久化问题（若用 persist 中间件，timer id 会被序列化）

**模块级变量**是 Zustand 处理此类副作用的标准模式，与 store 实例同生命周期。

### 5.2 MAX_HISTORY 测试踩坑

**现象**：连续调用 105 次 setValue 后，undo 应能回退 104 次（history 截断为 100），但实际 undo 返回 0 次。

**根因**：setValue 的 useCallback 依赖 `[equalityFn, value, history, currentIndex]`，连续调用时闭包中的 value/history/currentIndex 是渲染时快照。第 2 次调用读到的是第 1 次调用前的 state，导致 history 栈错乱。

**修复**：引入 valueRef/historyRef/indexRef，setValue 中读取 ref 而非闭包变量，useCallback 依赖简化为 `[equalityFn]`。

**经验**：React hook 中连续调用 setState 时，务必用 ref 保存最新值，不能依赖闭包变量。这是 React 函数式组件的固有陷阱。

## 八、技术沉淀

### 8.1 React hook 连续调用 setState 的正确模式

**问题**：连续调用 setState 时，闭包中的 state 是渲染时快照，不反映中间更新。

**错误写法**：
```typescript
const fn = useCallback((newVal) => {
  setValue(prev => prev + 1);  // OK，updater 模式
  setCount(count + 1);  // 错误！count 是闭包快照
}, [count]);  // 依赖 count 导致每次渲染重建
```

**正确写法**：
```typescript
const valueRef = useRef(value);
useEffect(() => { valueRef.current = value; }, [value]);

const fn = useCallback((newVal) => {
  const cur = valueRef.current;  // 从 ref 读取最新值
  // ...
}, []);  // 无依赖，永不重建
```

### 8.2 Zustand 模块级定时器模式

**适用场景**：store 中需要在状态变化后延迟执行副作用（如 3 秒后清空完成消息）。

**模式**：
```typescript
let timerId: ReturnType<typeof setTimeout> | null = null;

function clearTimer() {
  if (timerId) { clearTimeout(timerId); timerId = null; }
}

// 在所有可能改变相关状态的 action 入口调用 clearTimer()
// 在设置新定时器前先 clearTimer()
```

**优势**：
1. 不污染 store state
2. 不被 persist 中间件序列化
3. 与 store 实例同生命周期
4. 显式的清理时机控制

### 8.3 React 18 StrictMode 下 updater 纯函数性

**规则**：setState updater 必须是纯函数，不能有副作用。

**反模式**：
```typescript
setCount(prev => {
  logAnalytics(prev);  // 副作用！
  sideEffectFn();      // 副作用！
  return prev + 1;
});
```

**正确模式**：
```typescript
setCount(prev => prev + 1);
useEffect(() => {
  logAnalytics(count);
  sideEffectFn();
}, [count]);
```

**理由**：StrictMode 下 React 会调用 updater 两次以检测纯函数性，副作用会执行两次导致 bug。

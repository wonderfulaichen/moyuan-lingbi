# 墨渊灵笔 Agent-Skill 架构模式分析报告

> 基于 WorkBuddy 平台 "主 Agent → 子 Agent → Skill → 系统级 Skill" 架构模式，
> 对墨渊灵笔（AI 辅助小说创作工具）的产品架构与用户体验设计进行映射分析。

## 二、主 Agent 与子 Agent 生态系统的角色定义

### 2.1 主 Agent：创作助手

**定义**：墨渊灵笔的顶层交互角色，用户感知的唯一"AI 搭档"。

| 属性 | 说明 |
|------|------|
| **定位** | 对话式写作搭档，不是工具面板 |
| **职责** | 理解用户意图、维护创作上下文、协调子 Agent 工作流、统一输出 |
| **心智模型** | 用户对他说话就像对一个资深编辑/写作搭档说话 |
| **路由逻辑** | 自动判断：用户的需求属于哪个子 Agent 的专业领域，必要时串行/并行调度多个子 Agent |
| **输出风格** | 统一人格，用一致的语调回应，不会暴露"现在切换到了 Agent X" |

**核心原则**：用户从来不直接对子 Agent 说话。用户只对创作助手说话。

### 2.2 子 Agent 定义

| # | 子 Agent | 专业领域 | 典型触发场景 | 用户是否需感知 |
|---|----------|----------|-------------|:---:|
| 1 | **大纲规划师** | 故事结构、节奏、章节划分、三幕式/起承转合 | 用户说"帮我规划一下这卷的章节" | ❌ 隐藏 |
| 2 | **章节写手** | 场景创作、叙事视角、细节填充、对话写作 | 用户说"帮我写这一章的开头" | ❌ 隐藏 |
| 3 | **角色审计师** | 人设一致性、角色成长弧、动机合理性、对话是否符合人设 | 用户说"检查一下这个角色有没有OOC" | ✅ 暴露 |
| 4 | **情节审计师** | 情节逻辑、伏笔埋设与回收、时间线一致性、因果关系 | 用户说"帮我看看有没有剧情漏洞" | ✅ 暴露 |
| 5 | **文风润色师** | 语言风格一致性、修辞优化、句式多样性、节奏控制 | 用户说"帮我润色这段文字" | ❌ 隐藏 |
| 6 | **世界观守门员** | 设定一致性、规则体系遵守、地理/历史/文化准确性 | 用户说"检查这个设定有没有矛盾" | ✅ 暴露 |
| 7 | **灵感挖掘师** | 创意发散、情节可能性、交叉联想、矛盾驱动 | 用户说"给我一些故事方向建议" | ❌ 隐藏 |
| 8 | **伏笔追踪员** | 伏笔登记、回收状态追踪、伏笔密度分析 | 用户说"我有哪些伏笔还没收？" | ✅ 暴露 |

### 2.3 子 Agent 暴露规则

| 暴露层级 | 条件 | 交互方式 |
|----------|------|----------|
| **完全隐藏** | 日常写作辅助、续写、润色、灵感发散 | 用户对创作助手说话，底层自动路由 |
| **按需暴露** | 用户主动提出专项需求（"检查一致性"、"追踪伏笔"） | 创作助手响应时提及查到的结果，但不介绍子 Agent |
| **明确暴露** | 用户开启"深度模式"或明确的审计/分析需求 | 界面出现"专项分析"标签，用户可看到这是哪类分析，但仍统一由创作助手呈现 |

**设计原则**：
- 80% 场景隐藏子 Agent（日常创作流）
- 15% 场景间接感知（"创作助手刚才做了一次角色一致性检查"）
- 5% 场景直接暴露（用户主动进入审查/分析模式）

## 三、Skill 体系的分类与生命周期

### 3.1 Skill 在墨渊灵笔中的映射

WorkBuddy 的 Skill 是**可被 Agent 调用的能力模块**。映射到墨渊灵笔：

| Skill 类别 | 示例 | 谁来用 | 用户能否自定义 |
|------------|------|--------|:------------:|
| **文风包** | 古风/现代/悬疑/轻小说风格预制包 | 章节写手调用 | ✅ 用户可以创建 |
| **体裁模板** | 玄幻/科幻/言情/推理的结构模板 | 大纲规划师调用 | ✅ 用户可以创建 |
| **检查规则集** | 角色检查规则/时间线检查规则/设定检查规则 | 各类审计师调用 | ⚠️ 高级用户可自定义规则 |
| **写作技巧** | 悬念设置/节奏控制/多视角切换技巧 | 章节写手+文风润色师调用 | ❌ 系统内置 |
| **场景引擎** | 战斗场景/情感场景/推理场景的生成模式 | 章节写手调用 | ❌ 系统内置 |
| **对话生成器** | 不同角色说话风格预制 | 章节写手调用 | ✅ 用户可训练 |

### 3.2 Skill 的生命周期

```
安装/激活 → 配置/定制 → 运行/调用 → 更新/迭代 → 卸载/禁用
```

| 阶段 | 用户操作 | 系统行为 |
|------|----------|----------|
| **发现** | 在 Skill 市场浏览/搜索 | 展示 Skill 描述、评分、兼容性 |
| **安装** | 点击安装 | 下载 Skill 包，注册到本地 Skill 仓库 |
| **配置** | 调整 Skill 参数（如文风强度、检查严格度） | 写入用户配置，AI 调用时读取 |
| **调用** | （用户无需操作） | 子 Agent 根据上下文自动选择合适的 Skill |
| **更新** | 接收到更新通知，选择是否更新 | 拉取新版本，保持兼容 |
| **卸载** | 在管理界面移除 | 从本地仓库移除，不再被 Agent 调用 |

### 3.3 Skill 与 Agent 的关系

```
         ┌────────────────────┐
         │     主 Agent       │
         │    创作助手         │
         └──────┬─────────────┘
                │ 路由/调度
         ┌──────▼─────────────┐
         │    子 Agent         │─── 每个子 Agent 有默认 Skill 配置
         └──────┬─────────────┘
                │ 选择与组合
         ┌──────▼─────────────┐
         │  Skill 能力层       │─── Agent 根据任务选择 Skill
         │  文风包|模板|规则集  │─── 可同时调用多个 Skill
         └────────────────────┘
```

**关系本质**：
- **Agent = Who**（谁在做：角色/身份）
- **Skill = How**（怎么做：能力/方法）
- 一个 Agent 可以装备多个 Skill
- 一个 Skill 可以被多个 Agent 调用
- Agent 决定 Skill 的组合与执行顺序

## 四、系统级 Skill 的设计（横切关注点）

### 4.1 映射自 RTK/TokenSaver 的模式

系统级 Skill 是**不归属于任何特定子 Agent，但被所有子 Agent 依赖**的基础能力。

| 系统级 Skill | 对应 RTK 的类比 | 功能 | 用户可见性 |
|-------------|----------------|------|:---------:|
| **StepMemory** | 上下文持久化 | 跨会话保持写作上下文（当前项目状态、最近的编辑、待办项） | ❌ 透明运行 |
| **Token 优化器** | TokenSaver | 智能管理上下文窗口，自动压缩/分段，确保重要信息不丢失 | ❌ 透明运行 |
| **版本历史引擎** | Git 版本管理 | 自动保存每次 AI 修改的版本，支持回溯、对比、恢复 | ✅ 可见（在版本管理界面） |
| **写作分析器** | 数据分析 | 统计写作进度、字数变化、写作速度、使用模式分析 | ✅ 可见（在数据面板） |
| **协作仲裁器** | 冲突解决 | 多人协作时处理编辑冲突、合并不同贡献者的修改 | ⚠️ 仅协作模式下可见 |

### 4.2 StepMemory 的特殊角色

StepMemory 在架构中扮演**连接层**角色：

```
写作会话1 ──→ StepMemory ──→ 写作会话2
    │                           │
    ▼                           ▼
 上下文A                    上下文A 自动恢复
 + 用户指令                   + 项目状态
 + AI 响应                    + 未完成待办
```

**关键特性**：
- 是系统级 Skill 中最核心的一个
- 决定了用户能否"上次聊到一半，今天继续"的连续体验
- 是所有子 Agent 共享的上下文存储
- 在主 Agent 层面做统一管理，子 Agent 只读/写自己关心的部分

## 五、用户体验设计原则（何时暴露/隐藏复杂性）

### 5.1 核心原则：分层透明度

```
Layer 0: 完全抽象 ── 创作助手是唯一界面
Layer 1: 间接感知 ── "我刚刚检查了一下角色一致性..."
Layer 2: 按需可见 ── "专项分析"标签页
Layer 3: 完全透明 ── 高级模式/调试模式
```

### 5.2 具体原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **日常创作零干扰** | 用户写稿、润色、续写时，底层 Agent 调度完全透明 | 用户说"帮我把这段扩写到500字"→ 创作助手直接输出，不解释过程 |
| **审计结果需署名** | 当子 Agent 发现问题时，以创作助手的口吻呈现，但附带领域标签 | ✅ "角色审计发现：主角在第三章的性格与设定有些偏差" |
| **用户主动触发才展开** | 审计/分析功能的入口是用户提出问题或点击按钮，而非 Agent 主动推送 | 用户问"我的设定有没有矛盾"→ 触发世界观守门员+角色审计师联合检查 |
| **进度告知建立信任** | 当操作耗时较长（>3秒），展示进度状态而非黑盒等待 | "正在检查全书的角色一致性……已扫描12章，发现2处潜在矛盾" |
| **紧急度决定干预方式** | 严重问题（如人设崩塌）主动提醒，轻微建议（如用词优化）仅标记不打扰 | 人设崩塌→气泡提醒；句式单调→仅在润色建议面板中显示 |
| **高级用户可解锁** | 提供"深度写作工作台"模式，展示子 Agent 视图和 Skill 装配状态 | 高级模式下可看到"当前活跃：大纲规划师 + 伏笔追踪员" |

### 5.3 界面原型示意

**默认模式（日常写作）**：
```
┌─────────────────────────────────────────────────┐
│  💬 创作助手                                      │
│                                                  │
│  用户：帮我写一下第5章的开头                        │
│                                                  │
│  创作助手：好的，第5章是主角第一次进入魔法学院，     │
│  我从神秘氛围入手怎么样？                          │
│  [写一段约300字的开头...]                         │
│                                                  │
│  [接受]  [重新生成]  [修改提示]                    │
└─────────────────────────────────────────────────┘
```

**审计模式（专项分析）**：
```
┌─────────────────────────────────────────────────┐
│  💬 创作助手                                      │
│  🔍 专项分析：角色一致性审计                       │
│                                                  │
│  已完成全书15章扫描，发现2处潜在矛盾：              │
│                                                  │
│  ⚠️ 第7章：主角对魔法知识的了解程度                 │
│     与第2章设定不符（刚入学 vs 已掌握高阶法术）      │
│                                                  │
│  ⚠️ 第12章：配角"林夜"的性格从冷静变为冲动           │
│     缺少过渡描写                                  │

└─────────────────────────────────────────────────┘
```

## 六、与当前产品架构的关系分析

### 6.1 Writer Agent / Auditor / Revisor 的关系映射

当前产品评审中提到的 Writer Agent / Auditor / Revisor 架构，与 Agent-SubAgent-Skill 架构是**嵌套关系而非替代关系**：

```
          Agent-SubAgent-Skill 架构（本报告）
                      │
        ┌─────────────┼─────────────┐
        │             │             │
    Writer Agent  Auditor      Revisor
    (= 章节写手)  (= 审计员群)  (= 润色师)
                     │
          ┌──────────┼──────────┐
          │          │          │
      角色审计师  情节审计师  世界观守门员
```

**对应关系**：
| 原概念 | 新架构中的角色 | 说明 |
|--------|---------------|------|
| Writer Agent | 子 Agent：章节写手（+ 可选调用灵感挖掘师） | 负责创作产出 |
| Auditor | 子 Agent 群：角色审计师 + 情节审计师 + 世界观守门员 + 伏笔追踪员 | 每个审计师有独立的专业领域 |
| Revisor | 子 Agent：文风润色师 | 后处理优化 |

**关键差异**：原来的三层线性流水线（Write → Audit → Revise），在 Agent-SubAgent 架构下变成了**星形调度**——主 Agent 可以根据需要任意组合、嵌套、并行调用子 Agent。

### 6.2 StepMemory 的角色

StepMemory 在这套架构中既不是 Agent 也不是 Skill，而是**基础设施层**：

```
主 Agent ──── 读写 ───→ StepMemory
  │                      │
  │                      ├── 项目当前状态快照
  │                      ├── 对话历史压缩摘要
  │                      ├── 未完成待办列表
  │                      ├── 用户偏好（文风偏好、检查严格度）
  │                      └── 活跃子 Agent 状态
  │
子 Agent ──── 只读 ───→ StepMemory（读取与自己相关的部分）
             只写 ───→ StepMemory（写入检查结果/创作产出摘要）
```

**关键区别**：
- 只有主 Agent 有权**写入**对话上下文和用户偏好
- 子 Agent 只读写自己专业领域的数据（角色审计师写角色检查记录，不写大纲）
- StepMemory 本身不是一个"角色"，而是一个"共享白板"

## 七、分阶段落地建议

### 7.1 阶段优先级矩阵

| 阶段 | 时间 | 交付物 | 与现有路线图的关系 |
|------|------|--------|------------------|
| **Phase 0** | 当前 | 单一创作助手（已有雏形） | 已有 AI 助手功能，做体验统一 |
| **P0** | 短期 | 主 Agent 路由 + 2-3 个子 Agent | 优先做审计类子 Agent（用户痛点最明显） |
| **P1** | 中期 | Skill 体系 + 更多子 Agent | 丰富创作能力，引入 Skill 市场 |
| **P2** | 长期 | 系统级 Skill + 高级模式 | 性能优化、协作、深度工作台 |

### 7.2 Phase 0：主 Agent 确立（当前即可推进）

**目标**：将现有的"AI 助手"改造为"创作助手"主 Agent

**具体动作**：
1. 统一人格——AI 助手的回复风格、语气、身份定义为"创作搭档"
2. 引入会话路由概念——同一入口处理所有写作相关请求
3. 建立子 Agent 注册规范（即使尚未实现多个子 Agent）

**不做**：
- 不要暴露子 Agent 给用户
- 不要重构现有代码

### 7.3 P0：子 Agent 先发部队

**目标**：实现最痛的 2-3 个子 Agent

**选择优先级**：
1. **角色审计师**（P0 最高优先级）— 人设崩塌是用户最大的写作痛点之一
2. **世界观守门员**（P0 第二优先级）— 设定一致性是第二痛点
3. **文风润色师**（P0 可选）— 高频使用但 AI 模型已能较好处理

**具体动作**：
1. 创作助手内部实现路由逻辑——根据用户请求分发到不同子 Agent
2. 子 Agent 以独立推理模块实现（独立 system prompt + 上下文切片）
3. 输出统一由创作助手呈现

**不做**：
- 不让用户选择子 Agent
- 不实现 Skill 市场
- 不实现并行调度

### 7.4 P1：Skill 体系 + 子 Agent 生态扩展

**目标**：建立 Skill 框架，扩展子 Agent 阵容

**具体动作**：
1. 设计 Skill 接口规范（输入输出格式、上下文要求）
2. 实现文风包 Skill —— 首批内置 Skill
3. 实现检查规则集 Skill —— 让审计类子 Agent 支持自定义规则
4. 扩展子 Agent：伏笔追踪员、情节审计师
5. 提供 Skill 管理界面（安装/卸载/配置）

### 7.5 P2：系统级 Skill + 高级模式

**目标**：完成架构基础设施，开放高级用户功能

**具体动作**：
1. 实现 Token 优化器系统级 Skill
2. StepMemory 工程化落地（跨会话持久化、自动摘要）
3. 版本历史引擎整合
4. 写作分析仪表盘
5. "深度写作工作台"高级模式

## 八、结论总结

### 8.1 核心推荐

1. **短期**：把现有的"AI 助手"升级为"创作助手"主 Agent，用统一的角色定位包装所有能力
2. **中期**：优先实现角色审计师和世界观守门员两个子 Agent——它们解决用户最大的写作痛点，且实现上可以与现有的一致性检查模块对接
3. **长期**：Skill 体系是让墨渊灵笔从"工具"进化为"平台"的关键——允许用户自定义文风包和检查规则

### 8.2 关键决策清单

| 决策 | 推荐 | 理由 |
|------|------|------|
| 用户是否感知子 Agent？ | 默认隐藏，审计场景暴露 | 日常创作不需要知道底层架构 |
| Skill 是否开放给用户？ | 有限开放（文风包、检查规则集） | 核心差异化能力系统内置，扩展能力开放 |
| StepMemory 放在哪一层？ | 系统级 Skill，主 Agent 管控 | 避免子 Agent 污染共享上下文 |
| 与 Writer/Auditor/Revisor 的关系？ | 嵌套（Auditor 拆分为多个审计子 Agent） | 单一 Auditor 的 scope 过宽，拆分后更精准 |
